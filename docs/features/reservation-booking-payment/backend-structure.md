# Backend structure

[SeatHold](../../../src/TicketBooking.Domain/Reservation/SeatHold.cs) fixes its initial state to Active; its private setter changes only through Convert, Cancel, or Expire. EnsureCanConvert validates a supplied owner ID against one UTC reading from the injected TimeProvider without mutation. EnsureCanConvertAt is internal and lets booking creation reuse that exact reading. Construction derives ExpiresAt from injected BookingTimingPolicy and authoritative session start. Constructor validation rejects empty/null/foreign/duplicate/unavailable session seats, snapshots their Money prices, and computes a same-currency TotalAmount. It accepts server-resolved inventory rather than input price snapshots.

[Booking](../../../src/TicketBooking.Domain/Booking/Booking.cs) has a private constructor; CreateFromHold is its public factory. It uses the hold's validation and copies immutable BookingItems, then sums Money snapshots with currency/precision checks. No price or total setters exist. The factory captures session/payment/cancellation deadlines from BookingTimingPolicy. Confirm, Cancel, and Expire use those immutable deadlines and an injected clock; transitions accept no caller deadline overrides. The factory never converts the hold itself; production persistence must use HoldConversionService to coordinate consumption and transfer.

[Payment](../../../src/TicketBooking.Domain/Payment/Payment.cs) has a private constructor; CreateForBooking starts Pending only from a PendingPayment booking before its captured payment deadline, using an injected clock, and copies its server-calculated Money total. No independent amount is accepted. Succeed/Fail share an internal completion guard. ProviderReference is nullable initially, can be recorded while Pending, and cannot be replaced. Repeated same-result/same-reference completion is a no-op; a conflicting terminal result throws. IdempotencyKey and Amount are immutable.

Tests: [SeatHoldTests](../../../tests/TicketBooking.Domain.Tests/SeatHoldTests.cs), [BookingTests](../../../tests/TicketBooking.Domain.Tests/BookingTests.cs), and [PaymentTests](../../../tests/TicketBooking.Domain.Tests/PaymentTests.cs). Tests cover deadline edges, owner mismatch, terminal states, duplicate items, Money precision/range limits, payment replays, and conflicting provider outcomes/references. [UtcTimeTests](../../../tests/TicketBooking.Domain.Tests/UtcTimeTests.cs) adds mixed-offset normalization, advancing clocks, single-read factory behavior, and null-clock checks.

Invalid hold/booking/payment transition tests assert exact DomainError values and preserved state/reference. Cancellation tests cover PendingPayment and Confirmed bookings one tick before, at and after cutoff; hold cancellation also preserves prices/items on rejection. [DeadlineInteractionTests](../../../tests/TicketBooking.Domain.Tests/DeadlineInteractionTests.cs) covers session-start caps, conversion near expiry, payment retries and a late success after booking expiration. The expanded domain suite passed 159 tests. This does not establish transaction coordination, allocation ownership or automatic refunds.

Hold creation now has HTTP contracts, FluentValidation, the Customer JWT policy, shared row locks and an atomic allocation transaction. Owner GET/DELETE hold routes now complement creation; booking/payment HTTP routes, pending-booking expiry workers, webhook checks and payment-provider adapters remain absent. [EF mappings and relational constraints](../local-persistence/FEATURE.md) now persist entity state and snapshots. TimeProvider is passed explicitly to time-sensitive operations; API registers TimeProvider.System. No entity stores a clock, and no business rule reads a static wall clock. The built-in clock abstraction adds no dependency package or external I/O. See [time conventions](../../time-conventions.md). The API binds the BookingTiming section at startup; see [timing configuration](../booking-timing/FEATURE.md).

## Customer hold endpoint

[HoldEndpoints.CreateAsync](../../../src/TicketBooking.Api/Reservation/HoldEndpoints.cs) registers the customer POST route from Program. [HoldValidation](../../../src/TicketBooking.Api/Validation/HoldValidation.cs) validates the selection before SQL. The handler obtains the customer only from ICurrentUser, uses ResourceOwnershipService before side effects, locks the session and event FOR SHARE, loads inventory without tracking, checks auditorium membership, currency and total limits, and constructs the domain hold using captured UTC time. Ordered calls to SessionSeatAllocationWriter.HoldAsync compare the loaded version/status and return the next token; SeatHoldItem.CaptureAllocationVersion records that token once. SaveChanges inserts the aggregate in the same transaction. A final expiry check precedes commit. No automatic conflict retry occurs.

HoldResponse exposes only explicit DTO fields, historical prices and the captured deadline; neither identity entities nor internal owner/version data are returned. Failures use the existing ProblemDetails middleware and error catalogue; OpenAPI lists 400/401/403/404/409/415/500, including the allocation-specific conflict codes. [AuthEndpointsTests.Holds](../../../tests/TicketBooking.IntegrationTests/AuthEndpointsTests.Holds.cs) exercises the real HTTP pipeline against isolated migrated PostgreSQL schemas.

Atomicity verification also uses [AuthEndpointsTests.HoldAtomicity](../../../tests/TicketBooking.IntegrationTests/AuthEndpointsTests.HoldAtomicity.cs). A test-only command interceptor pauses after the first actual seat UPDATE without changing production behavior. A separate connection verifies committed visibility; a competing HTTP request can then claim the later seat before the paused request resumes. This deterministically exercises rollback after a successful earlier claim, rather than only rejecting inventory already unavailable at lookup. No sleeps or production retry paths are used.

## Owner-only retrieval and cancellation

HoldEndpoints.GetAsync reads the hold/items in one no-tracking query, then invokes ResourceOwnershipService before returning the stable HoldResponse. It returns stored history even for terminal or elapsed holds, without implicitly expiring/releasing them. POST now returns the implemented GET route as Location. All hold responses use Cache-Control: no-store.

HoldEndpoints.CancelAsync starts a transaction, locks the hold scalar ID FOR UPDATE, loads its items and checks stored ownership before any mutation. It locks the session FOR SHARE, checks Active state and the captured expiry, then releases items in stable ID order through SessionSeatAllocationWriter.ReleaseAsync using their saved AllocationVersion and expected Held status. Missing/unknown tokens or wrong-session inventory fail closed with seat_not_available. Eligible future Scheduled sessions release to Available; other session states release to Unavailable. After lock waits, SeatHold.Cancel checks the clock again; a final post-save expiry check precedes commit. Hold state and every release roll back on any conflict/failure. Original item tokens remain historical claim evidence; released inventory stores the advanced version. No token refresh/retry or row deletion occurs.

[AuthEndpointsTests.HoldOwnership](../../../tests/TicketBooking.IntegrationTests/AuthEndpointsTests.HoldOwnership.cs) covers owner history, other Customer/Admin denial, expiry boundaries, terminal states, legacy/stale tokens, concurrent cancellation, reacquisition fencing and rollback after save failure/expiry. No schema change is required.

## Background expiry

[HoldExpiryWorker](../../../src/TicketBooking.Api/Reservation/HoldExpiryWorker.cs) is registered from Program with AddHoldExpiryWorker. [HoldExpiryOptions](../../../src/TicketBooking.Api/Reservation/HoldExpiryOptions.cs) bounds work/polling at startup. The singleton [HoldExpiryBatchProcessor](../../../src/TicketBooking.Api/Reservation/HoldExpiryBatchProcessor.cs) holds no DbContext: it creates a scope for bounded candidate selection and a separate scope per candidate. [HoldExpiryReleaser](../../../src/TicketBooking.Infrastructure/Persistence/HoldExpiryReleaser.cs) owns the one-hold transaction and reuses SessionSeatAllocationWriter. The query uses a filtered active-expiry index and a keyset cursor to avoid starvation by invalid old records. No background task captures a scoped HTTP context or user.

[AuthEndpointsTests.HoldExpiry](../../../tests/TicketBooking.IntegrationTests/AuthEndpointsTests.HoldExpiry.cs) and [HoldExpiryConfigurationTests](../../../tests/TicketBooking.IntegrationTests/HoldExpiryConfigurationTests.cs) cover transactional behavior and hosted-service lifetime. HTTP test hosts register processing services without automatically starting the worker; worker tests explicitly run batches/service lifecycle for deterministic manual-clock assertions. The production Program starts the service automatically. See [worker contract](hold-expiry-worker.md).

Worker-independent eligibility is verified by [AuthEndpointsTests.HoldUse](../../../tests/TicketBooking.IntegrationTests/AuthEndpointsTests.HoldUse.cs): it leaves cleanup unrun, loads an Active hold from PostgreSQL, and tests validation, conversion, booking creation and cancellation one tick before/at/after its captured expiry. Rejected operations preserve state, deadlines and snapshots; owner DELETE returns hold_expired, and still-held inventory cannot be reallocated. GET continues to expose owner-only stored history. The existing shared domain expiry guard supplies this behavior without waiting for a worker transition.

## Repeated cleanup and conversion serialization

CancelAsync checks stored ownership before returning 204 for an already-Cancelled hold, without touching inventory or checking a new deadline. Domain Cancel/Expire matching repeats preserve terminal history; other lifecycle guards remain strict. [HoldConversionService](../../../src/TicketBooking.Infrastructure/Persistence/HoldConversionService.cs) is registered scoped in Program and uses the same hold-first transaction/locking protocol as cancellation and expiry. It transfers Held allocations with retained versions, captures new BookingItem tokens and saves booking/Converted status together; post-wait/post-save deadline checks roll back late work. No production booking HTTP endpoint is introduced.

SeatHoldConfiguration now marks Status as a concurrency token, protecting stale tracked state saves in addition to command row locks. [AuthEndpointsTests.HoldConversionRaces](../../../tests/TicketBooking.IntegrationTests/AuthEndpointsTests.HoldConversionRaces.cs) uses a test-only conversion adapter and deterministic gates to check every winning transition, no partial booking/transfer on failure and stale-save rollback. Domain tests cover owner-authorized cleanup replay and independent booking-token capture. See [the protocol](hold-cleanup-conversion.md).

Additional lifecycle integration coverage in [AuthEndpointsTests.HoldLifecycle](../../../tests/TicketBooking.IntegrationTests/AuthEndpointsTests.HoldLifecycle.cs) verifies that two holds for one customer with different prices and currencies remain isolated across GET, cancellation and expiry. It also verifies policy denial for a real stored owner using a fresh roleless JWT. A test-only PostgreSQL trigger rejects multi-seat item insertion after allocation/header writes, exercising real database rollback/savepoint behavior and a successful independent retry. All trigger/function DDL is scoped to the fixture's generated schema and removed by fixture cleanup. No production behavior changes are introduced by these tests.

[AuthEndpointsTests.ParallelHolds](../../../tests/TicketBooking.IntegrationTests/AuthEndpointsTests.ParallelHolds.cs) adds HTTP-level twenty-customer contention for one available seat. A test-only reader barrier requires all twenty distinct PostgreSQL backend/transaction IDs before releasing allocation reads. The test expects one success, nineteen seat_not_available conflicts and exactly one saved allocation belonging to the successful caller.

[AuthEndpointsTests.OverlapAndExpiryRaces](../../../tests/TicketBooking.IntegrationTests/AuthEndpointsTests.OverlapAndExpiryRaces.cs) adds deterministic {A,B}/{B,C} races with either winner and either input order, plus due expiry overlapping a validated conversion's commit. The extra reader/commit interceptors are test-fixture-only and disabled in other cases. No production behavior/schema changes are introduced.

## Redis hold responses

[RedisHoldCache](../../../src/TicketBooking.Infrastructure/Caching/RedisHoldCache.cs) implements the Application [IHoldCache](../../../src/TicketBooking.Application/Reservation/IHoldCache.cs) contract using IDistributedCache, System.Text.Json and TimeProvider. [AddHoldCaching](../../../src/TicketBooking.Infrastructure/Caching/HoldCacheRegistration.cs) registers the singleton adapter and StackExchange.Redis provider from ConnectionStrings:Redis. Owner GET queries only the hold header before using the cache; misses load items separately. Create caches after commit; cancellation, conversion and expiry invalidate after commit. See [TTL, fallback and race handling](hold-caching.md).

HoldEndpoints.GetAsync now uses RepeatableRead for header/item consistency and commits before returning a cache hit or populating/removing a missed/terminal response. RedisHoldCache.GetAsync is read-only even for invalid entries. All other cache mutations remain explicitly after CommitAsync. Commit-failure regression tests cover both read and command boundaries; see [commit ordering](hold-caching.md#database-commit-boundary).
