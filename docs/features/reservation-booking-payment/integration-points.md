# Integration points

| Direction | Interface/payload | Authority and failure behavior |
| --- | --- | --- |
| Booking factory → SeatHold | Internal EnsureCanConvertAt(userId, now) with the factory's UTC clock reading; immutable Items/SessionId. | Reservation owns validity; invalid owner/state/time rejects. In-process read, no aggregate mutation or retry. |
| Future Application → Reservation/Booking/Payment | Domain constructors and lifecycle methods. | Caller supplies trusted identity/session-start data, passes injected BookingTimingPolicy/TimeProvider at creation, and establishes cross-object consistency. HoldEndpoints implements the hold transaction; booking/payment handlers remain absent. |
| Items → Catalogue | Selected SessionSeat objects, SessionSeatId, and captured Money PriceSnapshot. | Catalogue owns inventory/current price; snapshots become historical facts. Constructor checks local availability/session membership; no authoritative repository lookup in constructors. Row updates now have [version fencing](../session-seat-concurrency/FEATURE.md); hold creation now coordinates claims and snapshots in one transaction; booking transfer/release transactions remain absent. |
| Payment → booking identity | CreateForBooking reads the PendingPayment booking ID and server-calculated Money total. | Booking owns its total/status. Factory verifies PendingPayment and its captured payment deadline using the clock, and derives amount/currency. Future Application must verify persisted authority and provider-reported amount/currency/signature/outcome. |

[Venue/Catalogue model](../venue-catalogue-model/FEATURE.md), [domain boundaries](../domain-boundaries/FEATURE.md), and [local persistence](../local-persistence/FEATURE.md) describe neighboring code. These are code dependencies and planned coordination boundaries, not external network integrations.

Same-instance payment replays do not provide API key uniqueness or protect provider calls. Future persistence must scope/enforce payment idempotency and ensure duplicate webhooks cannot create repeated effects. No key-scope or provider-retry policy is invented here. The [retention/late-payment decision](../booking-timing/seat-retention-and-late-payments.md) requires owner-checked release and durable idempotent compensation; no worker, reconciliation record, or refund execution exists yet.

Plan sequencing: phase 6 adds RabbitMQ/MassTransit, OutboxMessage, and ProcessedMessage; phase 7 adds notifications/cancellation application policy and Refund processing. Their entity schemas/workers/events are intentionally not implemented now. Changing snapshot or transition contracts can affect those later consumers.

Customer hold HTTP integration: bearer JWT → Customer policy → ICurrentUser/ResourceOwnershipService → authoritative session/event/inventory lookups → BookingTimingPolicy/SeatHold snapshots → SessionSeatAllocationWriter claims → PostgreSQL commit. Existing Admin session edits lock the session FOR NO KEY UPDATE and conflict with the hold's shared session lock; edits after creation reject allocated inventory or hold history. The anonymous seat map exposes Held status and current inventory prices, while the hold response carries its captured prices. There is no external network/provider call or request idempotency mechanism in this flow.

Owner routes reuse the Customer policy and stored UserId checks without an Admin bypass. GET reads independent historical snapshots, so later inventory repricing does not affect its DTO. DELETE coordinates the hold row lock, session shared lock, domain cancellation clock guards, and retained-version release writer in one PostgreSQL transaction. Conversion/expiry handlers serialize hold transitions with the same hold lock and never substitute a refreshed inventory token. Booking/payment/provider integrations remain absent.

System expiry bypasses HTTP caller identity because it is a server lifecycle operation, not a customer authorization path. Program → BackgroundService → bounded batch processor → dedicated scoped HoldExpiryReleaser → injected TimeProvider/domain Expire plus version-fenced writer → one PostgreSQL transaction. It shares the hold lock protocol with DELETE/future conversion and leaves Converted holds untouched. Failures are logged and retried only with the original retained ownership token, never a refreshed inventory version. No external message broker/provider integration is introduced.

HoldConversionService combines persisted ownership checks with the booking domain factory, authoritative session time, transfer writer and stored booking claim tokens in one transaction. Cancellation/expiry that observe Converted do not release any of its inventory; stale hold tokens cannot match the advanced booking tokens. Matching cleanup repeats do not call the allocation writer again. EF status predicates provide a second guard against stale tracked saves. Public booking/payment, provider and refund integrations remain absent.
