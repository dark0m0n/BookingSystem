# Known gotchas

**Observed admin boundary:** Admin eligibility for GET /api/admin/bookings does not authorize reading another owner’s /api/bookings/{bookingId}, changing a booking or impersonating an owner. The list includes owner GUIDs only on its separate admin contract. Offset pages may shift across requests; the route supports only page/pageSize, with no search/status/owner filters in this version.

**Observed pagination limit:** Count and page use one snapshot within each request. New bookings between separate page requests can shift offset pages; there is no cross-request snapshot cursor. GET returns the stored status, so elapsed PendingPayment may remain visible while expiry cleanup is delayed; reads never perform cleanup.

**Observed:** Booking cleanup can lag PaymentDeadline until a polling transaction commits. Domain confirmation/payment initiation already reject at equality; availability remains Held meanwhile. Null/stale legacy claim tokens cause safe skipped expiry with logging, not guessed ownership or token refresh. See [worker behavior](booking-expiry-worker.md).

**Observed compatibility limit:** EnforceUniqueBookingSourceHold leaves existing bookings with null SourceHoldId because the old schema did not record the relationship. The unique index protects known sources; it cannot identify historical duplicates. New factory calls always populate the reference. Do not manually null out known source IDs.

- **Observed:** A repeated POST /api/bookings after successful conversion returns 409 hold_not_active, including if the client lost the first response. There is no request idempotency key or source-hold replay lookup; preserve the successful BookingResponse. Owners can inspect GET /api/me/bookings or follow a known booking Location; source-hold replay lookup remains absent.

- **Observed:** Creating a Booking does not consume the hold. Repeated factories can create multiple in-memory bookings until conversion. HoldConversionService now persists one booking, transfer tokens and Converted status atomically under the hold lock. Direct factory persistence bypasses that command and is unsupported for production. SourceHoldId now has a unique database index, preventing a second persisted booking for the same known hold; legacy rows have no inferred source.
- **Observed:** Passing the deadline while a hold is still marked Active does not automatically change its status. Conversion and cancellation still reject at ExpiresAt; an explicit Expire call is needed to set Expired. The API worker now performs this transition and release transactionally; cleanup may lag until a polling pass commits.
- **Observed:** Confirm checks PendingPayment and now < captured PaymentDeadline. It does not prove payment success, amount match, or seat allocation. Future Application must validate these and commit seat changes atomically; do not expose the method as an unguarded endpoint.
- **Observed:** Payment result replay is safe only on the same in-memory attempt/reference. Two Payment objects can share an idempotency key; no database/provider/API deduplication exists yet.
- **Observed:** Cancellation reads current UTC time and checks its captured cutoff. The [timing policy](../booking-timing/FEATURE.md) defines configurable windows at creation; later setting changes do not change existing objects. Callers must still supply the authoritative session start at creation, and future mappings must persist snapshots.
- **Observed:** Cancelling a paid booking does not refund a payment or release seats. Refunded enums are reserved, and Refund/messaging entities are deferred to their phases.
- **Inferred-risk:** Holds snapshot prices from supplied SessionSeat objects and calculate currency-aware totals. This does not prove the objects were loaded from authoritative storage or establish globally unique seat holds. The customer creation endpoint now performs server-side lookups and atomic claims; server conversion now coordinates transfer; pending-booking release now uses retained booking tokens at the captured payment deadline; [row-level concurrency](../session-seat-concurrency/FEATURE.md) now provides the fenced write primitive.

The transition interpretation, exact equality boundaries, no-reopen failed payments, and duplicate callback policy are explicit design choices derived from the plan's flows. The [retention/late-result policy](../booking-timing/seat-retention-and-late-payments.md) now decides allocation lifetime and compensation requirements; payment/confirmation database coordination, provider reconciliation, refunds, and messaging remain unimplemented. Clock-driven UTC and exact-deadline behavior is unit-tested. No real provider, database round-trip, HTTP authorization, background expiry, concurrent request, or webhook behavior is verified by domain tests.

- **Observed:** HTTP-created holds leave inventory Held after expiry until the expiry worker commits a release. Owner GET and DELETE cancellation are implemented, and POST advertises the GET Location. Automatic expiry release is now implemented for valid retained claim tokens.
- **Observed:** Legacy items have null AllocationVersion. Their ownership cannot be safely released/transferred by reading a newer token from inventory; owner DELETE therefore rejects release with 409 seat_not_available; a compatibility policy is still needed.
- **Observed:** POST is not idempotent. A repeated request for the same held seats returns seat_not_available rather than extending the original deadline.
- **Observed:** Hold creation validates database availability atomically, but does not implement booking transfer, payment or automatic sale completion. The domain-only verification caveats above do not describe the new PostgreSQL HTTP tests.

- **Observed:** DELETE is cancellation, not physical deletion. It returns 204, including an authorized repeat after cancellation, without another inventory write. Historical items and the original expiry remain readable by the owner.
- **Observed:** At/after expiry, cancellation returns 409 hold_expired and leaves allocation intact for the expiry worker. GET may still show stored Active status with a past expiresAt; it does not renew the hold or advertise inventory as free.

- **Observed:** Legacy/null, stale or otherwise inconsistent allocations remain Active and allocated when cleanup cannot prove ownership. The worker logs the failure and advances its cursor so later holds continue; operators must reconcile these records without refreshing claim tokens.
- **Observed:** Batches run once per poll, not an unbounded backlog drain. Defaults examine at most 100 holds then wait five seconds; restart after changing settings. Multiple API instances safely skip each other's hold locks.
- **Observed:** Worker startup does not apply migrations. Missing schema/database errors are logged and retried. Apply the migration chain through local startup before running the API.

- **Observed:** Cancellation replay still requires the original owner, even for Admin. Converted/Expired states do not become Cancelled on replay.
- **Observed:** Service commands require a fresh scoped DbContext and the hold-first lock protocol. Status concurrency catches stale tracked saves, but callers must not blindly retry with a refreshed status or allocation version.
- **Observed:** Legacy booking items have null claim tokens. They cannot authorize a future release without a safe reconciliation policy. New bookings store SourceHoldId but no HTTP replay-success lookup is implemented; normal repeated conversion conflicts instead.

- **Inferred-risk:** Cache invalidation can fail or race an Active fill after a terminal commit. Database-header ownership/state checks on every GET prevent later reads from trusting terminal stale data; a subsequent owner read removes it. Redis is never inventory authority.
- **Observed provider behavior:** Redis key TTL has whole-second resolution and may expire early near the hold deadline. Misses reload PostgreSQL without extending ExpiresAt. A Redis outage adds cache timeout latency but does not undo committed lifecycle work. See [cache details](hold-caching.md).

- **Observed contract:** Cache lookups do not clean up invalid entries before database commit. A failed hold-read transaction leaves application-managed cache data untouched; the next successful read repairs/removes it, or the original Redis TTL expires it. Cache fills/removals do not run when CommitAsync fails. See [commit-order coverage](hold-caching.md#database-commit-boundary).

- **Observed contract:** A vanished hold key does not mean a seat is free, and a retained key does not extend a hold. During worker lag, deadline guards reject use while inventory remains Held. Redis outages or lost expiry notifications cannot block PostgreSQL polling/release; clients must use the server state rather than key existence. See [Redis independence](hold-expiry-worker.md#postgresql-authority-and-redis-independence).
