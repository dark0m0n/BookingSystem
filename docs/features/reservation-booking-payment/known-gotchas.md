# Known gotchas

- **Observed:** Creating a Booking does not consume the hold. Repeated factories can create multiple in-memory bookings until conversion. Application must persist one booking and convert the hold atomically with durable correlation/uniqueness; that step is absent.
- **Observed:** Passing the deadline while a hold is still marked Active does not automatically change its status. Conversion and cancellation still reject at ExpiresAt; an explicit Expire call is needed to set Expired. No worker or seat release exists yet.
- **Observed:** Confirm checks PendingPayment and now < captured PaymentDeadline. It does not prove payment success, amount match, or seat allocation. Future Application must validate these and commit seat changes atomically; do not expose the method as an unguarded endpoint.
- **Observed:** Payment result replay is safe only on the same in-memory attempt/reference. Two Payment objects can share an idempotency key; no database/provider/API deduplication exists yet.
- **Observed:** Cancellation reads current UTC time and checks its captured cutoff. The [timing policy](../booking-timing/FEATURE.md) defines configurable windows at creation; later setting changes do not change existing objects. Callers must still supply the authoritative session start at creation, and future mappings must persist snapshots.
- **Observed:** Cancelling a paid booking does not refund a payment or release seats. Refunded enums are reserved, and Refund/messaging entities are deferred to their phases.
- **Inferred-risk:** Holds snapshot prices from supplied SessionSeat objects and calculate currency-aware totals. This does not prove the objects were loaded from authoritative storage or establish globally unique seat holds. Server-side lookups and full database allocation transactions are still required; [row-level concurrency](../session-seat-concurrency/FEATURE.md) now provides the fenced write primitive.

The transition interpretation, exact equality boundaries, no-reopen failed payments, and duplicate callback policy are explicit design choices derived from the plan's flows. The [retention/late-result policy](../booking-timing/seat-retention-and-late-payments.md) now decides allocation lifetime and compensation requirements; database execution, provider reconciliation, refunds, and messaging remain unimplemented. Clock-driven UTC and exact-deadline behavior is unit-tested. No real provider, database round-trip, HTTP authorization, background expiry, concurrent request, or webhook behavior is verified by domain tests.
